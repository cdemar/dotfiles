# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal macOS dotfiles, managed with GNU Stow and Homebrew. There is no build or test suite; "running" a change means re-linking and reloading the affected tool.

## Commands

All via the `Makefile`:

- `make install`: install essentials from `Brewfile`, then `make link` (new machine)
- `make install-all`: essentials plus personal apps from `Brewfile.apps`
- `make apps`: personal apps only
- `make link` / `make unlink`: stow / unstow every package into `~`
- `make sync`: `git pull` then re-link
- `make update`: upgrade all Homebrew software
- `make status`: show outdated Homebrew packages (Neovim plugins are checked with `:Lazy check` inside Neovim)

Reloading after edits: `reload` (alias for `source ~/.zshrc`); WezTerm reloads its config automatically on save; Neovim needs a restart (plugin changes go through `:Lazy`).

## Layout: Stow packages

Each top-level folder is a Stow package whose contents mirror `~`, e.g. `nvim/.config/nvim/init.lua` → `~/.config/nvim/init.lua`. Packages linked by `make link` are listed in the `PACKAGES` variable in the `Makefile` (`zsh wezterm nvim ssh`). Adding a new tool means creating `<tool>/<path-relative-to-home>` and adding `<tool>` to `PACKAGES`.

`ssh/` holds only a non-secret `~/.ssh/config` (1Password SSH agent). `.gitignore` blocks private keys, `known_hosts`, and `config.local`; never commit anything else under `ssh/`.

Brewfiles are split deliberately: `Brewfile` holds only what these configs depend on (e.g. ripgrep, fd, lazygit, tree-sitter-cli for Neovim; powerlevel10k, zoxide, fzf, eza, fnm for zsh). Personal apps unrelated to the configs go in `Brewfile.apps`. When a config starts depending on a new CLI tool, add it to `Brewfile`.

## Neovim architecture

- `init.lua` loads `cdemar.core.options` → `keymaps` → `autocmds` → `cdemar.lazy`, in that order (options sets the leader key before any plugin mappings).
- `lua/cdemar/lazy.lua` bootstraps lazy.nvim and auto-imports every file in `lua/cdemar/plugins/`; each file returns a lazy.nvim spec. New plugins go in a new or existing file there. `lazy-lock.json` pins plugin versions and is committed.
- `lua/cdemar/profile.lua` is the one place that differs between machines. It returns the `personal` or `work` table selected by `NVIM_PROFILE` (default `personal`). `~/.zshenv` is deliberately not part of the repo, so on a work machine it has to be created by hand with `export NVIM_PROFILE=work`. Each profile defines:
  - `parsers`: Tree-sitter languages, consumed by `plugins/treesitter.lua`
  - `servers`: LSP name → Mason package name; `plugins/lsp.lua` installs the Mason packages and calls `vim.lsp.enable` on the keys
  - `tools`: extra Mason packages (formatters), also installed by `plugins/lsp.lua`
  - `web`: toggles the JSX/HTML tag plugin in `plugins/treesitter.lua`

  To add language support, edit the profile(s) rather than the plugin files. Formatters themselves are mapped per filetype in `plugins/formatting.lua` (conform.nvim, format on save; Markdown is intentionally excluded so notes are never rewritten).
- Leader mappings are grouped by prefix: `a` Claude Code (`plugins/claudecode.lua`), `b` buffers, `f` find, `g` git, `h` git hunks, `s` splits, `m` format, `o` Obsidian (group declared in `plugins/editing.lua`), plus single-key `<leader>d` (diagnostic float) and `<leader><space>` (smart picker). Keymaps live next to the plugin they belong to (lazy.nvim `keys`); only general editor mappings go in `core/keymaps.lua`. Check for an existing prefix before adding a new mapping.
- `claudecode.lua` connects to Claude Code running in a separate WezTerm pane (`claude --ide`), not a terminal inside Neovim.

## Shell and secrets

- `zsh/.zshrc` is ordered on purpose (Homebrew → p10k instant prompt → history → tools → aliases → secrets → zsh-syntax-highlighting last); keep new additions in the matching section and keep startup fast, since it runs on every pane.
- Secrets come from 1Password on demand via `op read` (e.g. the `awsenv` function), never hard-coded or loaded at startup.
- `zsh/.p10k.zsh` is generated by `p10k configure`; prefer regenerating over hand-editing.

## Style

Config files are heavily commented in plain language explaining *why* each setting exists; match that tone when adding to them.
